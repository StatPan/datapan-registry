# Upstream catalogue detail diagnostics

Processor detail failures are recorded as a small `failure_diagnostic` object on unresolved worker outcomes and checkpoint detail records. The only persisted values are fixed codes and, for a provider HTTP response, an observed 400–599 status. Exception messages, response bodies, URLs, query strings, tokens and exception class names are not stored.

The current codes distinguish `timeout`, `transport_error`, `provider_http_error`, `response_bytes_cap`, `unsafe_redirect`, `contract_or_parse_error`, `missing_link_detail_operations`, `unsafe_or_unregistered_operation_host`, `observation_mismatch` and `unexpected_error`. The latest observed failure remains attached to its source and guide fingerprints through bounded retries. A later successful enrichment clears it. A changed source or guide contract, or the existing new-observation retry epoch, clears the old cause along with its retry history.

For timeout, transport and provider HTTP failures, let the existing reservation and retry limit govern another attempt; use the HTTP status only to distinguish a provider response from a connection failure. For response-size, redirect, contract, missing-operation, host and observation failures, preserve the baseline and fix the bounded processor/source contract before requesting further detail. For `unexpected_error`, use the run and sealed checkpoint evidence to route a scoped code review. Startup recovery remains owned by the existing artifact-bound processor recovery workflow; do not repeat public detail calls to recover missing error text.

Checkpoint `detail_failure_counts` counts unresolved rows by their latest observed cause; it does not count HTTP requests. `detail_reason_unavailable_count` counts unresolved rows without a known cause, including rows that were not attempted and historical records created before diagnostic persistence. `detail_unattempted_count` separates rows with no request in the current invocation. Use `attempts_consumed` and the reservation fields for request-budget accounting.

When a reason is unavailable, the processor does not assign one from missing logs or old records. Operators should use the existing run artifact, checkpoint, reservation and recovery workflow to decide the next bounded action. Do not repeat detail requests solely to recover historical error text. These diagnostics describe worker outcomes; they do not create an observation, make a candidate ready, permit canonical promotion or change publication authority.
