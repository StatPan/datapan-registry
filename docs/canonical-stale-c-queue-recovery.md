# Scheduled canonical C queue recovery

The recovery controller runs only for the trusted scheduled `reconcile` entry of `canonical-update-promotion.yml`. It may reserve and cancel at most one eligible queued schedule attempt after proving the current controller and target use the same literal workflow-level concurrency group. A durable reservation is written before cancellation. Later invocations only read back that reservation; they never issue another cancellation request.

The recovery command writes one attempt-scoped receipt to `.datapan/ci/canonical-stale-c-queue-recovery/<run-id>/<attempt>/receipt.json`. Its exit code is zero only for `no_eligible_target` and `native_cancel_confirmed`. A failed proof, uncertain state write, unresolved reservation, failed or missing native readback, or receipt-write failure exits nonzero. Restart receipts copy the target workflow digest from the validated immutable reservation and preserve its original request disposition; a reservation with missing authority remains blocked and cannot issue another cancel. A no-action result is an ordinary success and does not set ACK, publication, or dispatch hints.

The workflow runs the recovery step before ordinary canonical C steps and sets `continue-on-error: true` on that step so those C steps still execute. At the end of the job, an `always()` scheduled-only gate requires both a successful recovery step outcome and a successfully uploaded receipt artifact, then validates the receipt schema, exact controller run/attempt/repository/workflow identity, and one of the two success outcomes. Missing or malformed receipt, blocked or unresolved outcome, native cancellation without exact terminal `completed/cancelled` and zero-job readback, or artifact-upload failure makes this final gate fail. That keeps a blocked recovery from ending a scheduled job green even when the ordinary C steps complete.

The recovery receipt and artifact use a separate path and artifact name from the existing per-mode canonical C terminal outcomes. Those C outcomes remain independently readable, and their own failed steps continue to fail the job. `workflow_run` and `workflow_dispatch` entries skip both new recovery steps and the final gate; their existing canonical C behavior remains in effect.
