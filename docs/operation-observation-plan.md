# Registry operation observation plans

The observation-plan compiler enumerates API operation identities already registered in Registry and separates three independent states: request-plan completeness, runtime binding, and admission. A complete request plan describes how a bounded read-only request is shaped. It does not bind a production credential, prove entitlement, reserve a provider quota, or admit a live call.

The current source set derives its denominator from five pinned scopes: the data.go.kr operation manifest and four registered supported-operation denominators. The data.go.kr manifest contributes its exact API operation identities; the four other sources contribute the operation IDs that Registry has actually registered while each scope remains `inventory_unknown=true`. Each operation carries the exact source-profile `adapter_id` separately from its Registry `source_id`. Provider-index adapter entries are host/adapter metadata, not operation identities. data.go.kr link operations are retained as a separate exclusion count and are not API request plans. The compiler checks exact ID sets, duplicate identities, supported exclusion keys, protocol/status arithmetic, and artifact hashes rather than using a historical operation total as its denominator.

Each index shard contains at most 256 plans, sorted by operation ID. `identity_set_sha256` is SHA-256 over the UTF-8 bytes of a compact JSON array containing the lexically sorted operation ID strings, with `ensure_ascii=false`, separators `,` and `:`, and no trailing newline. The release `manifest.json` binds the index and every shard by path, byte count, and SHA-256; the index in turn binds the source manifest, source snapshots, source profiles, and denominator artifacts. Consumers must verify the release-manifest entry before following the index's shard references.

## Request authority

An incomplete plan remains non-admitted and names the missing fields. A production request plan may be complete only when digest-bound evidence establishes an operation-specific HTTP method, HTTPS transport and exact endpoint, complete parameter inventory, each parameter's location and cardinality, an explicit bounded value strategy, authentication placement, request limits, and a response assertion. Explicit endpoint ports are retained as written; omitted ports stay omitted and are never normalized into an explicit default. HTTP-only endpoints remain incomplete unless a separately reviewed secure route is established. A reviewed policy may classify a precisely scoped documented GET or HEAD as read-only only when the same official operation document binds its exact summary/title and retrieval/list/search purpose, the policy records its rationale and RFC 9110 §9.2.1 basis, and no mutation or action-selector evidence conflicts. This policy classification is separate from provider facts; the compiler does not rewrite the operation-document effect as `read_only`. HEAD cannot complete a body-observation contract. SOAP plans state the HTTP method separately from the SOAP action and include the SOAP version, envelope namespace, operation QName, body encoding, and any SOAP-header authentication QName. SOAP action text alone does not establish a read-only operation.

Value strategies are explicit and evidence-backed. A bounded integer has minimum, maximum, and selection semantics. A relative year has an anchor, offset, and allowed year bounds. Reviewed enum/literal values are either present as reviewed non-secret values or referenced by an exact digest-bound evidence pointer. Credential values never appear in Registry plan records; credentials are represented only by runtime references in a private runtime binding.

The ten existing Health canary selectors and their reviewed bounded-parameter strategies are copied into `legacy_policy` records with their exact policy pointers. Reusable reviewed effect profiles can apply only to an exact source/provider/protocol/method scope and still require each selected operation's own documented method, title, and retrieval-purpose facts. The compiler does not infer required/optional cardinality from an empty parameter list and does not promote `registry_default_get` to method authority. Operation-document sidecars contribute only individually digest-bound facts with source locators; unknown or service-level-only method evidence remains unknown, and document evidence alone does not create a complete request plan.

## Reviewed policy and response assertions

`policy/operation-observation-policies.v1.json` is the Registry-owned input for reviewed operator choices. A direct row is bound to the full registered identity tuple (`source_id`, `operation_id`, provider, protocol, dataset ID, operation name, and upstream operation key), the exact operation-document artifact path/SHA/byte count, and one per-operation response assertion artifact. A reusable profile can cover multiple operations only when each operation independently matches its documented source selectors and every strategy and assertion fact resolves exactly. The compiler compares endpoint, operation-specific method, effect, authentication, parameter names, locations, requiredness, cardinality, and data types to captured document facts before emitting a complete request contract. A changed identity or source fact invalidates the output. It never reads example/default values as safe request values.

The policy selects bounded request strategies, local request size/time/request-count limits, and, when separately reviewed, runtime credential reference, shared non-secret quota buckets, and observation period. `credential_reference` identifies a credential-store entry without containing a secret. Quota scope keys identify a shared budget (for example a provider or credential group) and are identical across operations that share that budget; they are not credential values or credential hashes. Each scope's limit set must be identical everywhere that scope appears. The compiler emits `request_plan.status=complete` only when the request facts and reviewed strategy are both complete. It emits `runtime_binding.status=bound` only when the policy includes all runtime fields. It never promotes admission: the resulting plan remains `not_admitted` until separate admission evidence exists.

`schemas/datapan.operation-response-assertion.v2.schema.json` defines the reviewed typed response union stored at `reports/operation-response-assertions/<operation_id>.json`. The plan remains v1 and points to the exact artifact and `#/assertion`; the policy pins its path, byte count, and SHA. Each of at most 16 branches binds exact HTTP statuses, response-root kind/QName, bounded member/type selectors, branch-specific schema assertions, code facts, and optional result-collection semantics. A selector can test a source-documented member as present or absent, its JSON/XML node type, or exact typed values. Registry rejects duplicate/obviously overlapping same-path selectors; distinct member paths may co-occur, so the consumer must select exactly one branch before validating its body. Zero or multiple matches, an unknown code, a missing selected field, or an invalid selected success body is indeterminate; the evaluator never falls through to another branch after validation fails.

The same artifact can instead use `assertion: { "mode": "observation_only" }` when the request itself is fully source-grounded and reviewed but response-health semantics remain unestablished. The plan uses `response_assertion.kind=observation_only`, `empty_result_semantics=not_applicable`, an exact assertion reference, and evidence references to the reviewed choice and documented request facts; it carries no accepted HTTP status list. This mode means no body, code, collection, or empty-result predicate was established. Every 2xx response is indeterminate with reason `response_semantics_unestablished`; a non-2xx response can be reported only as an HTTP failure. It can never report healthy status or credential success. It preserves a complete request plan separately from runtime binding and admission. The current evidence checkpoint has one such complete request plan; that is request-construction coverage only, not health or live observation coverage.

Each selected required field carries its exact path, type, cardinality, and source references. A JSON Pointer resolves one node; its cardinality therefore describes node presence, not array length. XML QName paths select element nodes only, count matching elements, and preserve direct scalar text without trimming or coercion. A result collection requires the exact JSON array pointer, or an XML container QName and relative item selector; an absent required container is schema drift, while a present container with zero rows follows the reviewed empty-result rule. When a branch has no result collection, `empty_result_semantics` is `not_applicable`: the evaluator does not infer emptiness from an empty JSON object, scalar text, or XML root child count, and still enforces the exact root and required-field predicates. `valid` and `invalid` apply only to an existing selected collection. The additive `not_applicable` value changes the plan-v1 schema bytes; consumers must pin the new exact schema digest, and consumers still pinned to the earlier digest reject that value under their older enum. JSON and XML evaluation is bounded to 1 MiB response bodies, 100,000 JSON tokens, and depth 64. If official documentation defines provider result codes, the assertion includes exact typed success/error sets; unknown values remain indeterminate. A code-free predicate is allowed only after a complete source schema and empty coded-field inventory, with an explicit reviewed `code_mode=none` rationale. That choice is not inferred from parser omission. Source-documented error meanings may map exact error values to the fixed safe categories; unmapped documented errors remain generic provider failures. A complete plan binds the assertion artifact and every selected document fact into its evidence refs, while the release manifest binds the sidecar, reviewed policy, v2 assertion schema/artifacts, compiler inputs, index, and all shards.

The v1 plan `response_assertion.kind` maps to the v2 assertion's `payload_kind` as follows: JSON to `json_contract`, non-SOAP XML to `xml_contract`, and SOAP XML to `soap_fault_free`. The latter still uses the typed XML predicates inside the assertion artifact; this plan field does not mean that an HTTP success status alone is sufficient.

## Runtime binding and quota scopes

A bound runtime policy has an opaque credential-store reference when authentication requires one, a `credential_scope_key` that matches exactly one credential quota policy, one or more explicit quota policies, observation period, and evidence references. `source_binding.adapter_id` tells a consumer which registered adapter is allowed to resolve that reference; consumers must not infer credential names from environment variables. No-auth plans carry neither a credential reference nor a credential scope key. Quota scope keys are stable non-secret bucket identifiers shared by every operation governed by the same budget. Each constraint carries its own limits; provider-wide, shared-credential, organization, and API limits can all apply to one operation. Consumers reserve all applicable scopes atomically. Different limits for the same `(scope_kind, scope_key)` are a validation error.

Quota digests are `SHA256(UTF8("datapan.quota-scope.v1\\0" + scope_kind + "\\0" + scope_key))`. For example, scope kind `credential` and scope key `synthetic:credential-group:local-test` produce `9edfd346f33fb2c2b2308b096260bb16a9c5dc8910c216095c7f23fb3cc78ddf`. A scope key is never a credential value, a credential hash, or a secret-derived identifier. Source counts such as request counts and historical canary budgets are not quota limits.

Admission requires a complete request plan and bound runtime policy plus admission evidence. An unknown provider inventory scope does not turn a known registered operation into an unknown ID, and it does not imply that the whole provider catalog is covered. Missing source evidence, runtime bindings, and admission are reported independently.

## Regeneration and verification

```sh
# First commit the compiler, schemas, parser, and sanitized document evidence.
# Then generate output against that immutable source commit:
python scripts/generate-operation-observation-plan.py --source-revision <compiler-source-commit-sha>
python scripts/register-operation-observation-plan-artifacts.py --write
python scripts/sync-release-schema-artifacts.py --write
python scripts/generate-operation-observation-plan.py --check
python scripts/register-operation-observation-plan-artifacts.py --check
python scripts/sync-release-schema-artifacts.py --check
python -m unittest tests/test_operation_observation_plan_fixtures.py
```

The checked-in synthetic REST and SOAP plans use `.invalid` hosts and an explicit `test_only=true` source binding plus method, read-only, input, authentication, quota, limit, and response declarations. They exercise compiler and consumer contracts without contacting a provider. The current set contains 12,666 currently known registered API-operation IDs: 12,662 data.go.kr rows from a source-complete manifest and four known IDs across four partial source scopes whose upstream inventory remains unknown. One request plan is complete in `observation_only` mode, 12,665 request plans remain incomplete, all runtime bindings are unbound, and all operations are not admitted. The 8,871 data.go.kr links and 138 provider-index adapter entries remain separate from API-operation identities. This is inventory reconciliation and request-construction groundwork, not proof that every Registry source is enumerated or live observation coverage.
